# 删除 context-prune

用户原话（2026-11-13）：「我本来是想说这个能帮我实现超长会话下的稳定性，但现在看来这对于超长会话其实没什么帮助」；「可以把这个扩展直接砍掉了」。适用范围：整个 `context-prune` 扩展（三条规则、三个 `ctx_*` 工具、提醒通道、`/context-prune`）。

## 证据

**294 个真实会话**（`~/.pi/agent/sessions`，按 system prompt 里的 `<session_file>` 段落识别加载过该扩展，168MB / 14.4k 个 tool result / 13,064 次请求）：末尾状态下 43% 的 provider 可见内容可剪（6.93M token），但 294 个会话里 peak prompt 只有 p90 252k、最高 697k，**只有 8 个文件出现过 compaction**。窗口从来不是约束，剪枝买不到它声称的稳定性。真实 nudge 52 条，35 个会话，1 轮内转化 20 条；`ctx_expand` 0 次、`ctx_search` 4 次。

**9 轮 A/B**（3 臂 × 3 轮；deepseek-flash，1M 窗口，每轮 4 × 268KB 原始工具输出进上下文，最后问三个只存在于原始输出里的精确事实）：

| 臂 | 请求 | peak 上下文 | 非缓存 input | 成本/任务 | 正确性 |
|---|---|---|---|---|---|
| 无扩展 | 41 | 279k | 349k | $0.149 | 72/72 |
| 只剪枝 | 58 | 182k | 577k | $0.219 | 71-72/72 |
| 剪枝 + 提醒 | 55 | 182k | 597k | $0.220 | 72/72 |

从这 9 条 run 反解出的实际价格：input $0.30/M、cacheRead $0.006/M（**50 倍**）、output $1.17/M（回代误差 <1%）。peak 降 35%、正确性不变，但每轮 pass 都要重写被剪的前缀，同样工作量贵 **47%**。一批剪枝只有在 `n ≥ (后续内容 / 剪掉量) × (input 价 / cacheRead 价)` 次后续请求之后才回本：本测试这个数是 150–250，实际每轮约 10 次。提醒通道买不到可测的成本收益（$0.220 vs $0.219），真实语料里它只驱动 4% 的剪枝量。

## 结论与边界

删除。不是因为实现有错——两处真实缺陷（nudge 提示里 `bash <id>` 的格式诱发 3 次错误 id 往返；`ctx_search` 摘录锚在"第一个命中的词"而不是整句，实测把 44.5KB 结果的摘要窗口停在 22KB 外的邻居行）在删除前已修，但没有服务对象。

本拍板只覆盖「1M 窗口 + cacheRead ≈ input/50」这个组合（用户 80% 的工作在此）。**没有验证**小窗口（272k 级，那时 compaction 会真的介入）与弱缓存折扣（cacheRead ≈ input/4）的供应商；若将来必须在那类环境跑长会话，当时的 harness 与数据在 `byissue/notes/2026-11-13-context-prune-ab.md`，是唯一值得重测的场景。
