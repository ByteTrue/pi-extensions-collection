What this change does: Persists bounded completion notices and restores them for the original parent session, with memory/disk deduplication. Two concrete defects remain in background output retention.

1. **[P2] Orphan recovery deletes output belonging to a pending notice.** At [background-terminal.ts:336](C:/Users/byte/workspace/pi-extensions-collection/background-terminal/background-terminal.ts:336), cleanupOrphan unconditionally removes the log. A transient failure removing the journal during [cleanupTaskMeta:225](C:/Users/byte/workspace/pi-extensions-collection/background-terminal/background-terminal.ts:225) can leave the journal while settlement successfully persists a completion. If the owner then crashes, the next startup finds a dead owner and missing/dead child and calls cleanupOrphan. Recovery runs before the pending-aware sweep at [background-terminal.ts:1203](C:/Users/byte/workspace/pi-extensions-collection/background-terminal/background-terminal.ts:1203), so the restored notice points to deleted output. Fix: apply pending-notice retention to orphan cleanup too, preserving the log when notice storage cannot be inspected. Add coverage combining metadata cleanup failure, a pending notice, and restart recovery.

2. **[P2] Starting another profile can sweep a pending result's log.** At [background-terminal.ts:169](C:/Users/byte/workspace/pi-extensions-collection/background-terminal/background-terminal.ts:169), the sweep reads pending IDs only from the current getAgentDir(), but [background-terminal.ts:102](C:/Users/byte/workspace/pi-extensions-collection/background-terminal/background-terminal.ts:102) places every profile's logs in the same temporary directory. Profile A can leave an undelivered completion and exit; after seven days, starting profile B deletes A's unjournaled log because B's notice store does not contain its ID. Reopening A restores a notice with a missing output file. Fix: make output retention discoverable across profiles, for example with a durable marker beside pending logs, or isolate each profile's output/sweep directory. Add a two-profile retention case.

Validation: Both mechanisms were confirmed using the current cleanup/sweep functions extracted into an in-memory Node VM, with filesystem operations mocked. The sweep check included an owning-profile control that preserved the same log. Existing metadata-failure and restart tests cover these conditions separately, not together; existing pending-ID coverage uses one profile.

Integration resolution: Both findings were reproduced as failing tests in `background-terminal/output-retention.test.ts` and fixed before release. New logs have a private `.log.profile` sidecar identifying their notice store. Both the sweep and orphan cleanup consult that store, including from another profile, and keep output when ownership or notice storage is unreadable. Acknowledged logs and obsolete sidecars are collected normally. Regression coverage includes both findings, corrupted stores/markers, acknowledgement, and marker cleanup.
